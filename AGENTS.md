# ChessQA Explorer repository guidance

This is the provider-neutral entry point for agents and contributors. `CLAUDE.md` points
here, and must remain in place for Claude Code compatibility.

## Start here

1. Read this file and `docs/README.md`.
2. Read `README.md` for the public product framing and data contract summary.
3. If the task touches generated data or chess semantics, read the sibling benchmark
   repository's `../chessqa-benchmark/AGENTS.md`,
   `../chessqa-benchmark/docs/STATUS.md`, and exporter tests.
4. Inspect the current code, local Next.js docs, tests, and git state before editing.

## What this repository owns

ChessQA Explorer is a static behavior browser for the 50-task smoke campaign. It is not
a leaderboard. This repository owns the presentation layer:

- the home heatmap and run summary;
- five category pages and model pages;
- board overlays, state-tracking steppers, trace dialogs, and responsive navigation;
- the public copy and visual framing; and
- the committed static snapshot under `public/data/`.

The sibling `../chessqa-benchmark` repository owns dataset construction, prompts,
inference, scoring, canonical result JSONL, SQLite ingestion, the export schema, and all
chess-answer parsing. Keep that boundary intact.

## Product and data invariants

- Always frame the 50-task sample using counts and explicit denominators. One task per
  task type is useful behavioral evidence but cannot support precise rankings.
- Preserve the distinction between `full_text`, `summary`, `plain`, and other
  `thinking_source` values. Never describe provider-summarized reasoning as raw chain of
  thought.
- Illegal moves are a first-class outcome computed by the Python exporter. The frontend
  renders that outcome; it does not decide chess legality.
- `lib/types.ts` mirrors the export contract from
  `../chessqa-benchmark/eval/export_web.py`. Producer changes should be tested in the
  benchmark repository first, then reflected here with consumer tests.
- `public/data/` is generated by running `make export-web` in the benchmark repository.
  It is committed deliberately so the public payload is reviewable, but it must not be
  hand-edited.
- Raw provider payloads and private metadata must never be added to the public data.
- The site remains a pure static export: no server, database, authentication, tracking,
  runtime secrets, or server-only data dependency unless a new architecture is
  explicitly approved.
- Preserve stable category anchors, run slugs, and deep-link query behavior when changing
  navigation or rendering.

## Architecture

- `app/`: App Router pages and metadata.
- `components/`: feature components; `components/ui/` contains generated shadcn/base-ui
  primitives.
- `lib/data.ts`: fetches committed static JSON.
- `lib/types.ts`: consumer side of the export schema.
- `lib/board.ts`: the only place export primitives become board overlays.
- `lib/outcome.ts`: outcome labels, styles, and category order.
- `exhibits.ts`: hand-curated public examples; chess-specific claims require Aron's
  review.
- `public/data/`: generated snapshot from the sibling exporter.

Avoid putting chess notation parsing or outcome inference into React components. If the
UI needs a new semantic field, design it in the exporter contract.

## Development workflow

```bash
npm install
npm test
npm run lint
npm run build
```

Use focused Vitest coverage for board-overlay and outcome-mapping logic, then run lint
and the static build for user-visible changes. Because the project uses
`output: "export"`, a successful build is part of the architecture check, not just a
compile check.

For visual changes, verify the home page, one dense Short Tactics category page, a model
page, a trace dialog, and narrow-screen navigation. Preserve keyboard access, readable
contrast, lazy trace loading, and stable layout during hydration.

Do not commit, push, deploy, or regenerate the public data unless the requested slice
explicitly includes that side effect. Preserve unrelated working-tree changes.

## Documentation practice

- `docs/README.md` explains the local documentation boundary and links to the durable
  cross-repository records.
- The benchmark repository's `docs/STATUS.md` is the shared current handoff. Update it
  when a slice changes the producer/consumer contract or project-wide capabilities.
- The benchmark repository's dated explorer spec and implementation plans are design
  history, not current checklists. Reconcile them against this repository's actual
  layout and installed versions.
- Make public claims evidence-based. Separate measured smoke facts, design choices, and
  future full-run ambitions.

## Working with Aron

Communicate directly and show the evidence behind behavior or UX claims. Aron owns the
chess interpretation of curated exhibits. Preserve the site's restrained behavior-
browser framing and ask for a decision when a change would turn it toward leaderboard,
publication, or full-run product territory.
